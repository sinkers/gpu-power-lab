O1 · the ceiling

Twelve ways to burn a Blackwell

Each rung runs one workload for a 12-second measured window against the enforced 1100 W limit, sampling NVML at 50 Hz. Nothing in this sweep ever set a throttle bit, and clocks stayed flat near 1935 MHz throughout — so every gap below the dashed rule is work the GPU was willing to do and the workload failed to ask for.

The finding that nearly didn't happen

A 528 W difference between two ways of saying "use the tensor cores"

The orange bars near the bottom are the same tensor workload written the obvious way — wmma, warp-synchronous matrix-multiply inside our own kernel. It draws 460.6 W. The identical nominal work issued through cuBLAS draws 988.8 W on the same silicon in the same session.

Warp-synchronous wmma simply cannot reach Blackwell's 5th-generation tensor core. Only cuBLAS emits the tcgen05 path. That distinction went into the harness on the strength of a reading of the PTX ISA the day before this run.

Counterfactual

Had we run the original ladder on this box, it would have reported 460 W, we would have concluded Blackwell's tensor cores were unremarkable, and we would have been wrong by more than a factor of two.

Method

How the workload is actually written

The measurement is a single C11 binary. One invocation runs one rung end to end — warmup, then a timed steady window, then a summary — and exits. Python only decides which rungs to run; no interpreter, garbage collector or allocator sits inside the measured window. A sampler thread polls NVML on a pinned core using absolute-deadline sleeps, so it does not drift, and it records both the driver-averaged and the instantaneous power counter on every tick.

The workload kernel uses warp specialisation. Every warp reads a 32-entry role map built from the --mix-* weights and then does one thing for the whole launch, so tensor cores, the FP32 pipe and the memory path are driven by different warps resident on the same SM at the same time.

runner/src/workload_powervirus.cuthe three roles, abridged
/* TENSOR - register-resident fragments, two independent accumulator
   chains so the MMA pipe never stalls on one dependency. */
for (int i = 0; i < inner; i++) {
    mma_sync(c0, a0, b0, c0);   mma_sync(c1, a1, b1, c1);
    mma_sync(c0, a1, b0, c0);   mma_sync(c1, a0, b1, c1);
}

/* FMA - eight independent FFMA chains: enough instruction-level
   parallelism to issue every cycle, high register pressure, but the
   build fails on any spill (a spill would silently turn this into a
   memory workload). */
for (int i = 0; i < inner * 16; i++) {
    x0 = fmaf(x0, m, c);  x1 = fmaf(x1, m, c);
    /* ... x2 .. x7 ... */
}

/* DRAM - 128-bit loads on a prime stride, ~1 MB apart, so every
   access misses L2 and no two warps share a cache line. */
const size_t stride = 65537;
for (int i = 0; i < inner * 4; i++) {
    float4 v = stream_buf[idx];
    acc += v.x + v.y + v.z + v.w;
    idx = (idx + stride) % stream_elems;
}

/* Nothing is ever checked. The accumulators are consumed by a branch
   that cannot be taken, purely so the optimiser cannot delete the
   loops it would otherwise see as dead code. */
if (keep == 1.2345678e-30f) sink[0] = keep;

Three details matter more than they look. Input buffers are filled with memset(0x3c) — the bit pattern for half-precision ≈1.0 — because the arithmetic must be numerically unremarkable, not correct. Kernel launches are queued eight deep before a synchronise, since a host round-trip per launch left the GPU idle and cost about 20% of achievable power on the first attempt. And the tensor role has two backends: our own wmma loop, and a concurrent cuBLAS GEMM stream. On Blackwell only the second reaches tcgen05, which is the 528 W difference reported above.

For the O2 transient test, the off phase is a real host sleep rather than a spin. The number being measured is the distance from the idle floor to the peak, so a busy-wait would quietly destroy it.

O1 · the surprise

Everything we learned on Ampere inverted

The same harness ran a week earlier on an A10G. There, plain FP32 FFMA was the strongest workload by a wide margin (75.3% of TDP) and the tensor path was the weakest (37.3%). On B300 the ranking is precisely upside down: tensor 90.4%, DRAM 70.9%, FFMA 37.5%.

And the mixing hypothesis died twice, for opposite reasons

The harness was built around a plausible idea: a workload driving tensor cores, FP32 pipes and memory simultaneously should out-draw one saturating any single unit. It is wrong on both architectures, and the mechanism differs.

  • On Ampere, every unit competes for warp slots. FFMA had the best watts-per-warp, so mixing gave warps away to units that used them worse.
  • On Blackwell, the cuBLAS GEMM is the strongest consumer and our kernel displaces its blocks off the SMs. tcgen05 being asynchronous and single-thread-issued genuinely does free the instruction stream — but the contended resource turns out to be SM residency, not issue slots.

The prediction registered before this run — that concurrent tensor+FMA exceeding FMA-alone would prove overlap — resolved no. 581.8 W beats FFMA's 412.1 W, but both sit far below tensor-alone at 988.8 W. The mix is dilution, not addition.

Interpretation

How this differs from training and inference

This is a deliberately unrealistic workload, and the ways it is unrealistic are the point. A power virus is what the silicon does when nothing is in the way; a real job is that same arithmetic with overheads attached. Reading the gap between them is more useful than either number alone.

The strongest rung here is not exotic — it is a large dense GEMM, the same operation at the heart of both a training step and an inference prefill. What the harness strips away is everything around it.

The practical consequence: every gap between a real workload and 90% is overhead, not silicon. Synchronisation barriers, collective waits, memory stalls, kernel launch gaps, straggler ranks, and the simple fact that a transformer is not one continuous GEMM. Each of those is a moment the power delivery system gets a rest that this harness refuses to give it.

That also explains why the decode phase behaves so differently. Token generation is memory-bound and latency-bound, which is why the DRAM-only rung — 70.9% of TDP, the second-highest single result here — is arguably a better proxy for a busy inference server than the GEMM is.

For grid purposes the distinction is the whole argument. A datacentre sized on measured training and inference load is sized on workloads that leave 10–30% of the ceiling unused. A tenant who wanted to could take that back, and could modulate it deliberately — which is the case for treating GPU fleets as a controllable load rather than a fixed one.

Reading this honestly

What these numbers are not

  • In-band only. A KVM guest has no BMC, so every figure is what NVML reported, not what the board drew.
  • One GPU, no fabric. NVLink and inter-die traffic contribute real watts on a populated node and nothing here.
  • Short windows. 12 s steady, one run per configuration. Enough to rank configurations; not enough to publish a number.
  • One suspect field. power_violation_us read 6.65×10⁹ µs, far longer than the rung, so it is almost certainly a since-boot counter rather than the intended delta. Excluded from every conclusion.

Next

Where the missing 105 W might be

The part was never power-limited, so roughly 105 W of headroom is workload shortfall rather than the controller clamping. Two untested paths could plausibly close it: FP8 and FP4. Both need cublasLtMatmul — cublasGemmEx cannot express them — and FP4 additionally requires the sm_103a architecture target, which the build already emits.

Beyond that: a populated 8×B300 node, where the fabric contributes and where phase-aligned duty cycling turns a 0.9 kW single-GPU swing into a node-level step worth putting in front of a grid operator.
